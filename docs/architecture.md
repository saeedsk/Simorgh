# Simorgh Architecture

See `project_simorgh_groundwork.md` at the repo root for the original design
brief, `docs/SOUL.md` for identity/values, `docs/EVOLUTION.md` for the
long-term roadmap, and `docs/BIOMIMICRY.md` for the biological grounding
behind several pieces below. This document tracks what's actually built.

## Core principles

1. **The Orchestrator** is the central routing/synthesis engine. It holds
   the persona's identity and delegates work to sub-agents.
2. **Sub-agent sandboxing.** Each cognitive function runs in isolation.
   Skill agents in particular execute in a separate OS process with no
   access to the orchestrator's in-memory state.
3. **Shared memory bus.** Sub-agents don't pass large context windows to
   each other; they publish/subscribe to shared state instead.
4. **Continuous state tracking.** The persona's mood and cognitive load are
   tracked as continuous vectors, not fixed discrete moods.
5. **No single point of starvation.** Cognition, memory, and stability each
   have a guaranteed-available floor (rule-based agents, local disk, an
   automatic reset) beneath any richer/networked layer built on top.
6. **Nothing self-modifies unsupervised.** Proposals, trials, and pending
   approvals are all things this codebase produces; merging one into the
   live source is always a human action, never an automated one.

## Implemented so far

| Piece | Module | Purpose |
|---|---|---|
| Soul | `docs/SOUL.md`, `src/orchestrator/soul.py` | The constitution: identity, personality, and the 8 priority-ordered Core Directives (Safety > Lawfulness > Loyalty > Corrigibility > Restraint > Stability > Growth > Transparency) everything else is checked against. |
| State machine | `src/orchestrator/persona_state.py` | Thread-safe `PersonaState` holding continuous `valence`, `arousal`, and `cognitive_load`, clamped to valid ranges, with bounded history. |
| Shared memory bus | `src/memory/shared_bus.py` | Publish/subscribe wrapper around a `PersonaState`. Any agent can `read()` the live mood or `publish_state`/`publish_delta` to change it; subscribers are notified synchronously with `(previous, new, source)`. |
| Sub-agent interface | `src/orchestrator/router.py` | `SubAgent` ABC (`handle(request, bus) -> AgentResponse`) and `Router`, which registers agents by name and dispatches requests to one or many of them. |
| Emotion agent | `src/agents/emotion/base.py` | Lexicon-based reaction to input text; nudges mood on the bus and returns a short reaction phrase. No LLM dependency -- part of the guaranteed-available floor. |
| Logic agent | `src/agents/logic/base.py` | When given a `CognitionRouter`, calls a real LLM (persona + mood + recent `ShortTermMemory` context folded into the prompt) for the actual conversational response. The prompt is built from two separate blocks -- `_IDENTITY_PREFIX` (short, tone-only, always maximally prominent) and `_CAPABILITY_REFERENCE` (tool/safety procedure, condensed) -- split after a live bug where ~80 lines of accumulated procedure diluted the tone instructions enough that ordinary small talk came back sounding flat and corporate; `_mood_phrase()` renders mood as natural language ("calm, nothing much going on") instead of raw `Valence`/`ArousalLevel` enum values for the same reason. Falls back to the original rule-based drafting -- unchanged, still the guaranteed floor -- whenever no `CognitionRouter` is given, a real provider raises, only the deterministic echo answered, or the tool-step budget runs out without a final answer. `main.py` wires this by default; every existing rule-based test still passes unmodified since `cognition` defaults to `None`. Given `web_fetch`/`sandbox`, also offers bounded `FETCH:`/`RUN:`/`READ:`/`LIST:` tools mid-conversation (`LIST:`, backed by `safe_list_dir`, lets Sim discover a real repo-relative path -- `RUN`'s sandbox runs in an isolated temp directory by design and can't see this repository at all); given an `activity_log`, also offers `RECALL:`; `REMIND:` (always offered) schedules a real one-off timer (`src/orchestrator/reminders.py`). Given `propose_skill_fn`/`propose_patch_fn`/`propose_batch_fn`/`plan_fn`/`propose_evolve_fn`/`use_skill_fn`/`news_fn`/`growth_fn` (injected closures from `main.py`, avoiding a circular import), also offers `PROPOSE:`/`PATCH:`/`BATCH:`/`PLAN:`/`EVOLVE:`/`USE:`/`NEWS:`/`GROWTH:` -- explicitly authorized conversational triggers for the *exact same* propose/patch/batch/plan/evolve/use/news/growth pipelines a typed command or the autonomous loop would call; no raw WRITE tool or shell exists here, ever, and every audit/test/commit gate is identical regardless of trigger (see `docs/SOUL.md`, "Conversational Self-Modification"). `USE:`/`NEWS:`/`GROWTH:` are the exceptions to "self-modification" in that name -- they run an already-applied skill, check/share tracked news, or share a recent self-improvement, none of which change any code -- but all three are wired the same injected-closure way for consistency. When `use_skill_fn` is given, `_build_prompt` also injects a live, freshly-`list_applied_skills`-read list of every currently-applied skill name (bounded at `_MAX_SKILLS_IN_PROMPT`, 40, with a "+N more" note past that) directly into the prompt on every turn -- closes a real gap where applying a skill wrote it to disk and memory but never told Sim's own conversational awareness it existed, leaving `LIST:`/`READ:` the only way to ever discover one, with no reason to think to. |
| Sandboxing framework | `src/sandboxing/sandbox.py` | `SandboxExecutor` interface plus `SubprocessSandbox`, a process-isolated, CPU/memory/time-bounded executor for running skill code. The sandboxed process never receives the `PersonaState` or `SharedMemoryBus` objects. |
| Skills agent | `src/agents/skills/base.py` | `SkillsAgent(SubAgent)` that runs request text through a `SandboxExecutor` and reports a small cognitive-load delta back through the bus. Registered by default in `build_router()`; reachable live via the CLI's `run <code>` command. |
| Persistent memory | `src/memory/long_term.py` | `MemoryStore` interface with `add`/`get`/`query`/`delete`; `JSONFileMemoryStore` (durable, local disk, fsync'd, compacts on delete) and `InMemoryStore` (non-durable) implementations. Continuity of record, not process -- see `SOUL.md`. |
| Short-term memory | `src/memory/short_term.py` | `ShortTermMemory`: a bounded, non-durable rolling window of recent turns (by count and rough char budget), rendered via `as_context()` for a future cognition prompt. Wired into `main.py`'s `history` command. `save(path)`/`load_and_clear(path)`: a one-shot JSON handoff across exactly one relaunch -- `os.execv` (see self-patching, below) wipes this in-memory object outright, so `main.py` saves it to `~/.simorgh/relaunch_context.json` right before a patch/evolve relaunch and loads-and-deletes it on the next startup, restoring the conversation instead of silently dropping it. |
| Cognition router | `src/cognition/provider.py` | `LLMProvider` interface, `CognitionRouter` with automatic failover, and `DeterministicFallbackProvider` -- a zero-dependency floor that guarantees `complete()` never raises even with every real provider unreachable. |
| Budget guard | `src/cognition/budget.py` | `BudgetGuard`: wraps any real `LLMProvider` with a durable (survives restarts, via `MemoryStore`), rolling-window call/spend cap, scoped to that provider's own records only (`_recent_records()` filters by the wrapped provider's name -- fixed after a live bug where two guards sharing one store, each wrapping a different provider, counted each other's calls). Exhaustion raises `ProviderUnavailable`, so `CognitionRouter` degrades to the free deterministic floor exactly like a provider outage. **Any real, paid provider must be wrapped in this before being registered** -- see `docs/BIOMIMICRY.md`, "Metabolic conservation under scarcity." |
| Gemini provider | `src/cognition/gemini_provider.py` | `GeminiProvider`: calls Gemini's stable `generateContent` API (not the beta Interactions API) via `google-genai`, lazily imported so it's never required unless actually used. Reads the API key only from `GEMINI_API_KEY`/`GOOGLE_API_KEY` -- never hardcoded, never logged. `main.py`'s `build_cognition_router()` wraps it in `BudgetGuard` (default: $1.00/50 calls per 24h, both overridable via env vars) before registering it; with no key set, this provider is simply absent. |
| Claude Code CLI provider | `src/cognition/claude_code_provider.py` | `ClaudeCodeProvider`: spawns `claude -p <prompt> --output-format json --disallowedTools "*"` (no pip dependency -- shells out to a separately-installed `claude` binary), billed against the caller's Claude subscription rather than the API. `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`/`CLAUDE_CODE_OAUTH_TOKEN` are stripped from the subprocess environment (Claude Code's own credential precedence ranks all three above the subscription OAuth session). `--disallowedTools "*"` removes every tool from Claude's context -- used purely as a text-drafting backend, never given file/bash access, and `--dangerously-skip-permissions` is never passed. Each call also runs from a fresh empty temp dir as defense-in-depth. `--bare` is deliberately never passed -- it skips keychain reads, and a normal macOS `claude login` session lives in the keychain; passing it made every call fail with "Not logged in" despite a valid subscription (live-caught, `docs/EVOLUTION.md` milestone 66), with the failure silently absorbed by `CognitionRouter`'s fallback to the next provider. Wrapped in `BudgetGuard` using the CLI's own reported `total_cost_usd` (via `BudgetGuard`'s `cost_usd` metadata override) and a call-count cap (default 30/5h) -- registered ahead of Gemini in `build_cognition_router()` per the creator's preference to use the flat-rate subscription first. |
| Health monitor | `src/orchestrator/health.py` | `HealthMonitor` inspects `PersonaState` history for pinned extremes, sustained overload, or oscillation, and auto-resets mood to neutral on a CRITICAL finding. Wired live into `main.py`: a CRITICAL reset now surfaces as part of the reply itself. |
| Reflection loop | `src/orchestrator/reflection.py` | `OutcomeLog` records action outcomes to a `MemoryStore`; `ReflectionAgent.reflect()` turns a sub-agent's elevated failure/correction rate into a `Proposal` -- data, never an automatic change, reviewed in aggregate. `ReflectionAgent.reflect_on_outcome()` does the same per single outcome, immediately, as a free heuristic (no LLM call) -- fires after every failed/corrected turn, not just periodically; durably logs `kind="takeaway"` when given a `MemoryStore`. Wired live into `main.py`. |
| Audit gate | `src/orchestrator/audit.py` | `AuditGate.review()` vets a `ModificationProposal` through three layers: a static denylist (innate immunity), a learned check against previously rejected proposals (adaptive immunity, via `MemoryStore`), and -- for new-skill subjects only (`src/agents/skills/`) -- a real sandboxed run. `soul.py`/`SOUL.md`/`audit.py`/`apply.py`/`self_patch.py` are always-rejected subjects -- the same gate serves both the skills pipeline and the self-patch pipeline, so widening self-patch's target scope never widened what's reachable here. `requires_human_approval` is `False` under current policy (creator-authorized, see `SOUL.md`) -- a passing verdict applies immediately via `apply_proposal`/`apply_source_patch`. A sandbox failure's rejection reason includes a bounded excerpt of the real `stderr`/`stdout` (`_MAX_SANDBOX_DETAIL_CHARS`, 500), not just the generic `(timed_out=.., exit_code=..)` summary -- live-caught: that summary alone gave a retry loop nothing to act on, so the same task kept failing the identical generic way across multiple attempts with zero improvement. The sandboxed-execution check itself is scoped to skill subjects specifically -- found live and taken to the creator directly before changing it, given what this gate is: `SubprocessSandbox.run()` executes with an empty environment in a bare temp dir, which is correct isolation for a standalone skill but structurally impossible to pass for a self-patch's normal cross-module imports (`ModuleNotFoundError: No module named 'src'`, every time, regardless of code quality) -- this was the primary reason real self-patches to existing files almost never succeeded. A self-patch subject skips this one check and is verified instead by `run_isolated_test_suite` immediately afterward (a strictly stronger real-execution check, against a full repo copy with the package intact); every other check here (denylist, protected-subjects, adaptive-immunity) applies identically to both classes, unchanged. |
| Apply | `src/orchestrator/apply.py` | `apply_proposal()`: the one place allowed to write a *new skill*'s code to disk, scoped to `src/agents/skills/` only (independently of AuditGate's own protected-subject check -- a second boundary). `apply_source_patch()`: the analogous entry point for the self-patch pipeline, scoped to `src/` generally, logging `kind="applied_source_patch"` plus the isolated test-suite summary that authorized the write. Neither runs `git commit`/`git push` -- applied changes are ordinary uncommitted working-tree changes. |
| Self-patching | `src/orchestrator/self_patch.py` | `SelfPatchAgent.draft_patch(subject, topic)`: same READ/DRAFT tool-loop pattern as `SkillResearchAgent`, seeded with the target file's *complete, untruncated* current content (`tool_protocol.read_file_for_patch`, a much higher ceiling than the chat-facing READ tool's -- seeding a "write the complete new file" prompt with a truncated prefix produced a genuinely broken draft, caught live for a 62KB file; `src/main.py` and `src/agents/logic/base.py` were also over the old, smaller cap), for a patch to *existing* source (not a new file). Returns `(proposal, reason)`, not just `proposal | None` -- `reason` (only set when `proposal` is `None`) distinguishes a non-retryable stop (`"deterministic_fallback"`, or a `"refused: ..."` target problem) from a real provider answering with something that wasn't valid Python, which `propose_self_patch` retries with feedback via the same `prior_reasons` mechanism an audit-gate rejection already uses, up to `max_attempts` -- caught live monitoring a real session where an ambitious creative-agenda task kept failing on attempt 1 despite budget headroom to retry. On the last of `max_tool_steps` (default 6, raised from 4 -- it needs more exploration room than `SkillResearchAgent`'s, not less, since it's revising a file that interacts with the rest of the codebase), the prompt is appended with a warning that no more tool calls will be honored (`_FINAL_TURN_HINT`, same pattern `LogicAgent`'s own loop already uses) -- without it, a model that spent every step exploring emitted one more `READ:`/`DRAFT:` marker anyway, and that raw marker text became the "final file content" verbatim, guaranteed to fail; confirmed live with a deliberately small, well-scoped patch request that still failed this exact way. `main.py`'s `propose_self_patch` also rejects a subject outside `apply.SELF_PATCH_SCOPE_PREFIX` (`src/` only) immediately, before ever drafting -- a `docs/`-scoped patch attempt used to burn a real drafting attempt and fail with a misleading "no real drafting intelligence available" instead of an instant, honest scope explanation. `run_isolated_test_suite()`: copies the repo to a temp dir, runs the entire test suite there both before and after applying the candidate, and requires an unchanged-or-better test count plus a clean exit. `check_main_py_invariants()`: a narrow, explicitly-not-a-prover structural check refusing a `src/main.py` patch that no longer visibly wires the audit/apply pipeline. `_docstring_regression_reason()`: applies to every self-patch subject, not just `main.py` -- compares the original file's module docstring (`ast.get_docstring`) against the draft's, and treats a substantial docstring now missing or shrunk under 30% of its length as a retryable failure (fed back via `prior_reasons`, same as invalid Python). Live-caught the same day the pipeline first worked end-to-end: five real, autonomous self-patches to three different core files all silently deleted the target's entire module docstring while otherwise passing the audit gate and the full test suite -- reverted, then fixed structurally rather than left as a one-off cleanup. `relaunch()`: spawns a `--self-check` subprocess (`main.py`) first -- imports everything and constructs the core objects without entering the loop -- and only `os.execv`s the current interpreter/argv (replacing the process for real) if that passes; a failure returns `RelaunchResult(succeeded=False, ...)` so the caller can `git_ops.revert_last_commit()` instead of leaving a broken commit. Reconstructs `[sys.executable, "-m", "src.main"]` explicitly for both the self-check and the real exec, rather than reusing `sys.argv` -- live-caught: for a `python3 -m src.main` launch (`sim.sh`'s own invocation), Python resolves `sys.argv` to the absolute *script path*, not `['-m', 'src.main']`; re-invoking that path directly runs it as a bare script, putting `src/`'s own directory on `sys.path[0]` instead of the repo root, so every `from src.... import ...` in the patched code failed regardless of how correct the patch was. This silently reverted every otherwise-successful self-patch to a non-hot-swappable file, and stayed hidden because the unit test suite always injects `exec_func`/`check_runner` rather than exercising the real subprocess/exec path. Driven by `main.py`'s `patch <path> <description>` command, the autonomous idle loop, `evolve <count> <goal>` (`propose_patch_batch`, below), or `LogicAgent`'s own PATCH/EVOLVE conversational markers (explicitly authorized, see `docs/SOUL.md`, "Conversational Self-Modification") -- all five call this exact function. For `patch` (not `evolve`) specifically, `main.py`'s `_relaunch_or_rollback`/`_attempt_hot_swap` try an in-process `DeploymentManager.hot_swap` first when the patched file is one of `_HOT_SWAP_TARGETS` (a file defining a live Router sub-agent -- `logic`/`emotion`/`skills`): every gate above (audit gate, isolated test suite, apply, commit) is identical, only the activation step differs -- a full relaunch only happens for a subject outside that narrow list, or if the hot-swap machinery itself can't proceed (module won't reload, candidate won't construct, no active version staged), in which case it falls straight through to the relaunch path unchanged. |
| Evolve (patch batch) | `main.py`'s `propose_patch_batch` | The `evolve <count> <goal>` command and `LogicAgent`'s EVOLVE marker: brainstorms up to `MAX_EVOLVE_COUNT` (10) real `(path :: description)` targets under `src/` (given the actual existing file list as context, never `src/agents/skills/`), then runs `propose_self_patch` once per target with `do_relaunch=False` (relaunching after item 1 would kill the process before items 2..N ran). Relaunches once, after the whole batch; on a self-check failure, rolls back every commit from the batch together via `git_ops.revert_commits_since` (a multi-commit range revert), not just the last one. The real-architectural-change counterpart to `batch`, which only ever creates new standalone skill files. |
| Git auto-commit | `src/orchestrator/git_ops.py` | `commit_applied_change()`: stages and commits exactly one applied file (never `-A`), attributed to "Simorgh" via per-command `-c user.name=`/`-c user.email=` flags (never touches the repo's persistent git config), `--no-verify` never used. `revert_last_commit()`: `git revert --no-edit HEAD`, the single-commit rollback half of relaunch verification. `current_commit_hash()`/`revert_commits_since()`: the multi-commit equivalent -- marks a known-good point before a batch of patches (`evolve`) starts, and reverts the whole range as new commits if the batch collectively fails its post-batch self-check. `git push` is never run by anything in this codebase. |
| Task queue | `src/orchestrator/tasks.py` | `TaskStore`: a durable, event-sourced work queue on the same `MemoryStore` (`kind="task_event"`) everything else uses -- a `Task`'s current state is folded by replaying its own history, the same append-only discipline every other kind follows. `add()`/`update_status()`/`pending()`/`unfinished()` (PENDING/IN_PROGRESS/BLOCKED not yet DONE/FAILED -- what makes "on restart, find pending task and resume" real). |
| Improvement discovery | `src/orchestrator/discovery.py`, `src/main.py` | `discover_improvements()`: turns existing signals (`ReflectionAgent`'s batched `reflect()` proposals, individual `reflect_on_outcome` takeaways) into persisted `PATCH_TASK`s, deduplicated against every known task (including finished ones, so an already-fixed issue doesn't resurface just because its log record still exists). Purely reactive -- it has nothing to say when nothing's gone wrong. `discover_creative_improvements()` (`src/main.py`) is the creative complement, tried by `_autonomous_action` only when the reactive pass finds nothing: one bounded, goal-less LLM call asks Sim to set its own agenda and propose ambitious architectural ideas, reusing `evolve`'s exact brainstorm/parse shape (`path :: description` lines) so the resulting tasks flow through the same audited `propose_self_patch` pipeline as anything else on the backlog -- deterministic-fallback-safe like every other drafting call here. |
| Task verification | `src/orchestrator/verification.py` | `verify_task_completion()`: an independent, separately-prompted "reviewer" LLM call -- distinct from `AuditGate` (safety) and the isolated test suite (regression), neither of which asks whether a change actually addresses the task it was meant to solve. Only ever downgrades an already-successful apply to BLOCKED; never a gate on whether code gets written. Defers to `passed=True` when no real provider is reachable, rather than blocking completion on an unanswerable question. |
| Autonomous idle loop | `src/orchestrator/autonomy.py` | `ActivityClock` (tracks time since the last CLI command) + `AutonomyController` (a daemon thread): once idle past a threshold, first checks whether it's time to proactively share a growth highlight, then a news highlight (`src/orchestrator/socializing.py`'s `GrowthSocializer`/`NewsSocializer`, each its own separate and usually much-longer pacing cooldown -- a no-op on most ticks), otherwise works the task queue -- discovering new work first if empty, otherwise the next pending/in-progress `Task`, and (via `main.py`'s `_reconsider_blocked_tasks`, once there's no fresh work at all) reconsidering a `BLOCKED` task for another attempt, up to `MAX_BLOCKED_RETRY_ATTEMPTS` before giving up on it for good -- through the *unchanged* `propose_skill`/`propose_self_patch` pipelines. Bounded by an idle threshold (default 10s), an action cooldown (default 3s), a daily action cap (default 2000) on top of the existing `BudgetGuard` caps, and `poll_interval_seconds` (default 1s, how often the daemon checks) -- retuned three times from direct creator feedback, always downward: 300s/600s -> 60s/150s ("sitting idle all the time"), then 60s/150s -> 20s/30s ("hyperscale... showing constantly progress"), then 20s/30s -> 10s/3s ("10X speed up" -- action_cooldown got the literal 10x since it's the knob that actually paces repeated actions; idle_threshold only 2x, deliberately, since a full 10x would read an ordinary mid-conversation pause as "idle" and start competing for attention constantly). The daily action cap was raised alongside each retune (20 -> 500 -> 2000) to stay comfortably above Gemini's own 1500-call/24h `BudgetGuard` cap so it never becomes the binding constraint; `DEFAULT_CLAUDE_CODE_MAX_CALLS`/`CLAUDE_CODE_WINDOW_SECONDS` (30 calls/5h, `main.py`) were never touched by any of the three retunes -- that unchanged cap, not this file's timing, is what actually protects the creator's flat-rate Claude Code subscription; a faster tick just reaches it sooner, after which the existing Gemini/deterministic-floor fallback carries the rest -- plus a failure-streak circuit breaker: an optional `last_action_succeeded` callback reports whether the last action's own pipeline actually reported `[APPLIED]`, and `max_consecutive_failures` (default 5) consecutive failures disables the loop and prints a loud notice rather than quietly grinding through the rest of the daily cap on a systematically broken pipeline; `autonomous on` resets the streak on manual re-enable. Every action is printed with an `[autonomous]` prefix and durably logged. `main.py`'s `autonomous [on|off|status]` gives live control (default: on, per the creator's explicit authorization -- see `docs/SOUL.md`, "Autonomous Idle Loop"); `status` also reports the current failure streak when nonzero. `digest()` (`ActionDigest`: total/succeeded/failed/unknown over a time window, default 24h) backs `main.py`'s `digest` command -- an on-demand rollup, so reviewing what the loop did doesn't require reading raw `log`/`tasks` output by hand -- and `run_cli()` also prints it automatically at startup whenever it's nonempty, so activity from an idle stretch surfaces without the creator having to ask. |
| Reminders | `src/orchestrator/reminders.py` | `parse_duration()`/`schedule_reminder()`: a one-off `threading.Timer` that prints a message after a delay, reusing the same "a daemon thread can print between prompts" pattern the autonomous loop established. Deliberately not durable (see `tasks.py` for that). Wired as the explicit `remind <duration> <message>` command and as a `REMIND:` marker in `LogicAgent`'s own tool loop (always offered), so plain conversational asks ("remind me to...") are understood too -- the CLI command only intercepts input when the token right after "remind " actually parses as a duration, so ordinary chat starting with that word falls through to conversation instead of being misparsed. |
| Activity log | `src/orchestrator/activity_log.py` | `ActivityLog`: adds two record kinds (`conversation_turn`, `tool_call`) nothing durably captured before, plus a read layer (`recent()`, `since()`, `since_last_turn()`, `format_entry()`) merging those with every other kind (outcomes, applied skills/patches, rejections, spend, fetches, interests, takeaways) into one chronological, colorized timeline. Backs the CLI's `log`/`log last` commands and `LogicAgent`'s RECALL tool. |
| Console style | `src/orchestrator/console_style.py` | `style(text, *names)`: minimal ANSI color helper, auto-disabled for non-TTY output or `NO_COLOR`. Purely cosmetic -- every caller must read correctly with color stripped. `LiveTicker`: a periodic "still working... (Ns elapsed)" status line (a daemon thread, default every 5s) for a long blocking call that would otherwise sit completely silent -- `self_patch.run_isolated_test_suite`'s two subprocess runs are the motivating case. `render_checklist(items, title)`: a compact, icon-prefixed checklist (pending/in-progress/done/failed) for multi-step work, reprinted as a whole block after each step changes -- `batch`/`evolve` now show one, updated after every item, instead of only a scrolling trail with no summary until the end. `format_diff_block(diff_lines, label)`: `format_code_block`'s sibling for a `difflib.unified_diff` -- +/- lines colored, bounded/truncated the same way -- backs `pending <path>`'s diff-by-default view. None of these three attempt an in-place, cursor-redrawn spinner/live-region (fragile across terminals, piped output, non-TTY logging) -- all print new lines instead, the same "print safely while the caller stays blocked" safety property reminders/the autonomous loop already rely on. |
| Web fetch tool | `src/tools/web_fetch.py` | `WebFetchTool.fetch(url)`: real, reviewed outbound network access -- deliberately hand-built, not LLM-drafted (`AuditGate`'s denylist blocks `urllib.request`/`http.client`/`requests` in any drafted skill precisely so this is the only path). http/https GET only; SSRF protection (blocks private/loopback/link-local/reserved/multicast resolved addresses); bounded timeout and response size; durable, rolling-window rate limit; every attempt logged (`kind="web_fetch"`). ## Data flow (current)

```
AgentRequest ──▶ Router.dispatch(name, request)
                     │
                     ▼
              SubAgent.handle(request, bus)
                     │
        (skills agent only) ─▶ SandboxExecutor.run(code)  [isolated process]
                     │
                     ▼
            bus.publish_delta(source, ...)  ─▶ PersonaState.apply_delta
                     │
                     ▼
              AgentResponse ──▶ OutcomeLog.record(...) ──▶ back to caller
```

Self-modification pipeline (all reachable from the CLI today):

```
SkillResearchAgent.draft_skill(topic) ──▶ ModificationProposal
                     │
                     ▼
        AuditGate.review()  [denylist ─▶ adaptive-immunity memory ─▶ sandbox]
                     │
              approved_by_automation?
                 │              │
                no              yes
                 │               │
          printed + dropped   apply_proposal()  [independent src/agents/skills/-only
                                 │                scope check + path-traversal guard]
                                 ▼
                    written to disk + MemoryStore(kind="applied_skill")
                                 │
                                 ▼
              ordinary uncommitted git change -- creator reviews via
              git diff/status and decides whether to commit; 'pending'
              lists what's been applied this way
```

`requires_human_approval` is `False` under current, creator-authorized
policy -- there is no separate approval step. This is unchanged from
`AuditGate`'s own checks (denylist, adaptive immunity, sandbox), and the
protected-subject list (`soul.py`/`SOUL.md`/`audit.py`) is unaffected --
see `docs/SOUL.md`, "Self-Improvement Philosophy."
