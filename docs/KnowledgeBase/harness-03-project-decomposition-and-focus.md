# Project Decomposition, Sub-Projects, and Staying Focused

Sources: [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) (orchestrator-workers pattern), [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works) (Plan Mode, interrupt/steer), the arXiv Claude Code analysis (graduated trust, reversibility-weighted risk), and general findings on agent drift: [Agent Drift: Quantifying Behavioral Degradation in Multi-Agent LLM Systems Over Extended Interactions](https://arxiv.org/pdf/2601.04170), [Technical Report: Evaluating Goal Drift in Language Model Agents](https://arxiv.org/pdf/2505.02709), [AI Agent Security Starts with Scope Control](https://cloudsecurityalliance.org/blog/2026/05/12/ai-agent-security-starts-with-scope-control).

## When a task is really a project

A single bounded task (Anthropic's prompt-chaining or routing patterns cover this) has a knowable shape in advance: a fixed, small number of steps, a clear input and output. A **project** is different in kind, not just in size: the actual steps required *can't be enumerated up front* because discovering them is part of the work — this is exactly the orchestrator-workers pattern's own criterion for when to use it ("subtasks can't be predicted in advance"). The practical test for "does this need project treatment, not just a bigger single task": can you write down the complete list of concrete steps *before* doing any of the work, with confidence that list won't change? If yes, it's a (possibly long) task. If discovering the plan is itself part of the work, it's a project, and it needs its own tracked plan, not a bigger prompt.

## Decomposition as its own phase, not a byproduct

Good harness design treats "figure out the plan" as a distinct phase with its own output artifact — not something that happens implicitly while executing step one. Claude Code's Plan Mode is the sharpest version of this: exploration and plan proposal happen with *no ability to execute at all* (Edit/Write/Bash structurally unavailable in that mode), and only after the human approves does a mode switch unlock execution. The value isn't just "the model thinks first" — it's that the plan becomes a real artifact the human (or, for an autonomous system, a separate review pass) can inspect *before* any of its consequences are irreversible.

A decomposition phase should produce:
- A small number of concrete, individually-scoped steps (not so many that tracking them costs more than doing them, not so few that any one step is itself an undecomposed project).
- An explicit ordering or dependency structure where it matters — some steps genuinely can't start before others finish (an implementation step that depends on a research step's conclusion), and a harness that doesn't track this can start the implementation step too early, on stale assumptions.
- A record of *why* each step is there, tied back to the original goal — this is what makes later drift-detection possible at all (see below): without a stated reason per step, there's nothing to check a step's continued relevance against.

## Hierarchical tracking: sub-tasks under sub-projects under a project

Real orchestrator-workers systems (and Claude Code's own evolution from `TodoWrite` to `Task`, file 01) converge on the same shape: a durable, hierarchical backlog where completion rolls up from children to parents, not a flat list. The properties that matter:

- **Rollup status is computed, not separately tracked.** A parent's "done" should be a pure function of its children's actual statuses (all children done → parent done; any child permanently failed → parent can't silently claim done) — never an independently-settable field that can drift out of sync with what its children actually did. A parent status field that *can* diverge from its children's real states *will* eventually diverge from them, silently, the first time an edge case isn't handled.
- **A child can spawn its own children.** Real work often reveals genuinely new sub-work mid-execution (a research step concluding "this actually needs two more steps, not one") — the hierarchy needs to support that without requiring the whole plan be re-decomposed from scratch.
- **Persistence survives a crash or restart.** An in-memory-only todo list (the original `TodoWrite` shape) is fine for a single session but loses everything the moment the process restarts; a project spanning longer than one continuous session needs its plan durable on disk, not just in the live context window.

## Staying focused: concrete anti-divergence mechanisms

The research on "agent drift" is consistent: long-running agents degrade gradually, not suddenly, and the failure mode compounds — one paper found behavioral degradation affecting close to half of long-running agents studied, a measured ~42% drop in task success rate, and roughly 3x more human intervention needed once drift set in. The mechanisms that measurably help, gathered across the sources above:

1. **Re-state the goal, don't just remember it.** A cited mitigation: mandate that the agent explicitly re-articulate the user's *current* goal before processing new input, specifically so a tangential stimulus (an interesting side-finding, an unrelated error message) doesn't quietly become the new focus. This is cheap and concrete: a periodic "what am I actually trying to accomplish, and does what I'm about to do serve that" check, not a vague instruction to "stay focused."
2. **Bound the exploration budget explicitly.** Every self-directed tool loop in this codebase already does this (`DEFAULT_MAX_TOOL_STEPS` in `self_patch.py`, `research_task.py`) — a hard ceiling on how many unsupervised steps happen before the loop is forced to either conclude or explicitly ask for more room. Unbounded exploration is exactly where drift compounds, because each additional unsupervised step is another chance to wander further from the original goal with nothing checking it.
3. **State scope boundaries up front, and make out-of-scope actions structurally harder, not just discouraged.** The reversibility-weighted-risk principle (file 01) is the general form of this: an in-scope, reversible action gets light oversight; anything touching a file, system, or capability *outside* the stated scope should trigger heavier oversight automatically, not rely on the model remembering the boundary from several steps back. Sim's own `AuditGate` (protected subjects, the denylist) is a version of this for its own specific risk surface (self-modification); the general pattern is broader than that one gate.
4. **Checkpointing and receding-horizon replanning.** Rather than committing to one full plan and executing it blind, periodically re-derive the plan from the current actual state rather than the plan as originally conceived — the original plan can go stale as new information arrives, and a system that never re-plans keeps executing an increasingly wrong plan with full confidence. Cited mitigation-effectiveness in the literature: 67–81% error reduction from combining checkpointing, risk budgets, and this kind of receding-horizon replanning together, not any single one of the three alone.
5. **Let a human interrupt and redirect without losing state.** Claude Code's own interrupt/steer mechanism (Esc to stop immediately, or type a correction that's read at the next natural pause) is a cheap, always-available circuit breaker against drift that's already been noticed by a human — the cost of building this is low, and it catches the cases automated drift-detection hasn't caught yet.
6. **Treat "the plan changed" as a distinct, loggable event, not a silent overwrite.** If a project's steps get revised mid-execution, that revision — and the reason for it — should itself be a durable record, the same append-only-log principle from file 01 applied to planning specifically. A plan that silently mutates leaves no way to later ask "why did this project end up doing something different from what it started out planning to do."

## The cost side of the tradeoff

None of this is free. Re-grounding checks, bounded exploration, heavier oversight on out-of-scope actions, and replanning all cost real tokens, real latency, or both — and the "start with a workflow, only add agent autonomy when the task genuinely needs it" principle from file 02 applies here directly: a task that's actually well-specified in advance doesn't need any of this machinery, and adding it anyway is pure overhead. The judgment call is specifically about *open-ended, long-horizon, self-directed* work — exactly the shape of Sim's own autonomous creative-agenda and project-tier work (see file 06) — where the risk of silent divergence is real and the cost of catching it early is much lower than the cost of an entire project quietly drifting off its original goal for many cycles before anyone notices.
