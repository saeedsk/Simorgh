# Building an Effective AI Agent Harness — North Star

This is a reference set for leveling up Simorgh's own harness — the machinery around the model that turns "an LLM that can answer questions" into "an agent that can reliably plan, execute, verify, and complete real work." It was researched specifically because the creator asked: how does an effective agent harness get built, how does Claude Code's own harness actually work in detail, and what would it take for Sim's harness to reach the same bar or better.

Read this as a design reference, not a spec to copy verbatim — Sim is a different kind of system (a persona-driven, self-modifying, mostly single-model system, not a general-purpose coding tool with a large user base generating telemetry), and the gap-analysis file is explicit about which patterns transfer directly and which need adapting.

## How this set is organized

1. **[harness-01-claude-code-deep-dive.md](harness-01-claude-code-deep-dive.md)** — the primary worked example. What Claude Code's harness actually is, architecturally: the agentic loop, the five human values and thirteen design principles that shape every decision in it, the five-layer context-compaction pipeline, the seven-mode permission system and its ML classifier, subagents (fork vs. fresh), checkpoints, Plan Mode, and the Task/TodoWrite planning layer.
2. **[harness-02-design-principles.md](harness-02-design-principles.md)** — general agent-harness design principles, grounded in Anthropic's "Building Effective Agents": the workflow-vs-agent distinction, the five composable workflow patterns, and tool/agent-computer-interface design.
3. **[harness-03-project-decomposition-and-focus.md](harness-03-project-decomposition-and-focus.md)** — how to split a goal into a real plan and sub-projects, and the concrete mechanisms that keep a long-running agent from diverging off-task.
4. **[harness-04-completion-and-verification.md](harness-04-completion-and-verification.md)** — what "done" actually means for an agentic task, verification-before-completion patterns, and how to avoid a multi-step effort silently stalling half-finished.
5. **[harness-05-subsystems.md](harness-05-subsystems.md)** — an iterative, subsystem-by-subsystem breakdown (context/memory, planning, tool-use/execution, verification, permissions, multi-agent orchestration, persistence) — what each does, one effective way to build it, and the real tradeoffs involved.
6. **[harness-06-gap-analysis-simorgh.md](harness-06-gap-analysis-simorgh.md)** — the actual point of this exercise: a concrete, file-by-file comparison of what Sim's harness already has against everything above, and specific, prioritized recommendations for closing the gaps.

## The single biggest idea, if you read nothing else

Claude Code's own architecture paper (cited in file 01) frames the harness as existing to serve five human needs — decision authority, safety, reliable execution, capability amplification, and contextual adaptability — and derives thirteen concrete design principles from them. The throughline across nearly all of it is **externalize what can be externalized**: don't make the model's own judgment the only thing standing between an action and its consequences. A permission system, a compaction pipeline, an append-only log, a checkpoint mechanism, a subagent boundary — every one of these is a piece of *harness*, not a piece of *prompt*, precisely because harness-level mechanisms are auditable, testable, and reliable in a way that "ask the model to behave" never fully is on its own. Sim already lives by a version of this principle (`AuditGate`, the isolated test suite, event-sourced `MemoryStore`/`TaskStore` are all harness-level, not prompt-level, guarantees) — the gap analysis is mostly about which harness-level guarantees are still missing, not about whether the philosophy is right.
