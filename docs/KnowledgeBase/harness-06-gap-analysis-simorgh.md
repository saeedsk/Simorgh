# Gap Analysis: Simorgh's Harness vs. This Research

This is the actual point of the exercise. Read files 01–05 first for the context each item below refers back to.

## What Sim already gets right (worth stating plainly, not just gaps)

Before the gap list, it's worth naming what Sim's harness already does that matches the research directly — several of these were arrived at independently, before this round of research, which is itself a useful signal that the underlying principles are sound rather than Claude Code-specific idiosyncrasy:

- **Append-only durable state** (file 01's own principle #6). `MemoryStore`/`TaskStore` are both event-sourced — every change is a new record, current state is folded by replay, nothing is ever mutated in place. `project_status()` (`src/orchestrator/projects.py`) computing a project's status as a pure function of its children's current statuses, never persisted independently, is exactly the "derived views recomputed from the record, never allowed to drift out of sync" principle from file 05 §7.
- **Defense in depth on the safety gate** (file 01's principle #3). `AuditGate.review()` (`src/orchestrator/audit.py`) layers a static denylist, an adaptive-immunity similarity check against prior rejections, and a sandboxed execution run — three independent techniques, matching the "multiple overlapping mechanisms, not one" principle directly. Self-patches additionally clear a real isolated-test-suite run downstream (`self_patch.py`'s `run_isolated_test_suite`), a second, structurally different verification layer for that class.
- **Deny-first, with a boundary that can't be argued around.** `PROTECTED_SUBJECTS` in `audit.py` is checked before anything else in `review()`, and covers the audit gate's own source alongside `apply.py`/`self_patch.py` — no proposal, however well-argued, can talk its way past a protected subject, matching file 01's "deny always wins over a more specific allow" exactly.
- **Isolated, summary-only delegation.** `ResearchAgent` (`src/orchestrator/research_task.py`) was *built this session specifically modeled on how Claude Code's subagents work* (its own module docstring says so) — a bounded READ/LIST tool loop whose intermediate exploration never becomes durable state; only the final written finding does. This is a direct, already-implemented instance of file 01's subagent-isolation principle and file 05 §6.
- **Bounded exploration.** Every self-directed tool loop (`SelfPatchAgent`, `SkillResearchAgent`, `ResearchAgent`) has an explicit `DEFAULT_MAX_TOOL_STEPS` ceiling with a "this is your last step" warning one turn early — file 03's "bound the exploration budget explicitly" mitigation, already in place.
- **A working reversibility mechanism**, just git-based rather than a separate checkpoint layer: every applied self-patch is its own auto-commit (never pushed), and a failed relaunch self-check triggers `revert_last_commit`/`revert_commits_since` (a multi-commit range revert for a failed `evolve` batch) — the same "revert a failed batch as new commits, never rewrite history" pattern file 04 describes for Claude Code's own equivalent case.
- **A failure-streak circuit breaker with a human checkpoint to resume.** `AutonomyController`'s `max_consecutive_failures` (`src/orchestrator/autonomy.py`) disables the loop after a run of failures that "looks systematic, not incidental," and only `autonomous on` (an explicit human action) resets it — file 01's "graceful recovery, reserving human attention for the unrecoverable" principle, concretely implemented.

## The gaps, prioritized

### 1. No genuine Plan-Mode-style separation between "explore/propose" and "execute" for a single PATCH_TASK

Claude Code's Plan Mode is a *structural* guarantee: Edit/Write/Bash are unavailable during planning, not just discouraged. Sim's `SelfPatchAgent.draft_patch()` tool loop mixes exploration (READ) and the eventual draft in one continuous flow, and once a draft clears `AuditGate` + the isolated test suite, it's written and committed automatically — there's no intermediate point where a full plan (not just a code diff) is presented for review before anything executes. `PROJECT_TASK`'s `decompose_project()` *is* a genuine planning phase for the project tier specifically (it produces a real plan artifact — child tasks — before any of them run) — but that's the exception, not the general case; an ordinary `patch <path> <description>` has no equivalent "propose, then approve, then execute" split at all. Given Sim's current policy (`AuditGate.requires_human_approval = False` by explicit creator decision) already accepts auto-apply for what clears the gate, a full Plan-Mode-style human-approval gate for every patch would contradict that policy — but a **narrower version is still worth having**: for a `PATCH_TASK` above some size/risk threshold (e.g. touching a file over N lines, or one flagged as security/safety-adjacent even if not in `PROTECTED_SUBJECTS`), require an explicit plan-and-narration step that's *shown* before drafting begins, even if it doesn't block on human approval — transparency (file 01 principle) without necessarily adding a blocking gate.

### 2. No context-compaction pipeline in any tool loop

Every bounded tool loop (`self_patch.py`, `research_task.py`, `SkillResearchAgent`) grows its prompt by simple string concatenation across turns, relying entirely on the hard step-count ceiling and `safe_read_file`'s per-call size cap to keep any single call bounded — there is no graduated shrink-before-summarize pipeline (file 01 §"Context management") at all. This is low-risk today specifically *because* the step ceilings are small (6 steps, mostly), but it's the first thing that will actually bite once a `RESEARCH_TASK` or a large `PROJECT_TASK` child genuinely needs more room to investigate — right now the only lever is "raise the step ceiling," which raises cost roughly linearly with no cheaper intermediate option. Recommendation: before reaching for a bigger step ceiling, a cheap first version of file 01's "budget reduction" layer — replacing an old tool-turn's full result with a short reference once several newer turns have superseded it — would buy meaningfully more room per dollar than a flat ceiling increase.

### 3. No drift/re-grounding check across a multi-tick PROJECT_TASK

A `PROJECT_TASK` can span many autonomous-loop ticks, potentially hours or days apart, with unrelated other work happening in between (other tasks, other self-patches changing the very code the project touches). Nothing currently re-checks, when a project's next child is picked up, whether that child *still* serves the project's original goal given everything that's happened since it was planned — `_resolve_project_task`/`next_unfinished_child` just pick the next non-terminal child in creation order, unconditionally. File 03's "re-state the goal, don't just remember it" mitigation has no equivalent here. Concretely: `run_task`'s `PROJECT_TASK`-adjacent dispatch path could, before working a child that's more than some age threshold old, make one cheap check — "given the project's own goal and what's changed since, is this child still the right next step?" — with the same deterministic-fallback-safe, non-blocking shape every other creative call already uses, rather than blindly trusting a plan that might be stale.

### 4. No dependency graph between project children, only a linear order

`decompose_project`'s prompt *asks* the model to order research steps before the patches that depend on them, and `next_unfinished_child` mechanically honors that order — but there's no explicit dependency data (a DAG), so the harness has no way to represent "child C needs both A and B done" versus "child C just happens to come after A and B in the list," and no way to notice if the model's own ordering was actually wrong (a patch step that silently assumed a research step's conclusion, placed before it by mistake). This is a real but lower-priority gap relative to #1–3: it would only matter once projects get non-linear (a genuine fan-out/fan-in shape), which nothing in the current design produces yet.

### 5. Verification is single-pass outcome-only, not iterative or trajectory-aware

`verify_task_completion` (file 04's own worked example) is a one-shot yes/no check against the final result string — it never sees what tools were called or in what order (file 04 §"Evaluate the trajectory"), and a failed verification doesn't trigger an immediate "here's specifically what's wrong, try again" iterate-with-feedback loop (file 02's evaluator-optimizer pattern) — it instead marks the task `BLOCKED` and leaves it for a *later*, separate reconsideration round to pick up cold (with the failure note as `prior_reasons` context, which does help, but isn't the same as an immediate tight iteration while the relevant context is still hot). A genuinely iterative evaluator-optimizer loop — evaluate, get specific feedback, redraft, re-evaluate, bounded by a small retry count, all within the same task attempt rather than spread across reconsideration rounds — would likely recover more genuinely-good-but-imperfect first drafts than the current blocked-then-retried-later shape does.

### Smaller, lower-priority notes

- **No lightweight, pre-commit checkpoint layer independent of git.** Lower priority than it looks: Sim's tool loops don't write real files until the final apply step, so there's structurally less mid-loop risk than Claude Code's per-edit-snapshot use case addresses — the git-commit-per-applied-change mechanism already covers the case that actually matters here.
- **No interrupt/steer for an in-flight autonomous action.** `autonomous off` stops the *loop* from starting new work, but there's no way to redirect a single in-progress drafting call the way Claude Code's Esc+correction works. Given Sim's own actions are already short (bounded tool steps, not long-running), the practical impact is smaller than it would be for a longer-running system — but it's a real gap for the moment a `PROJECT_TASK` child does end up taking a while.
- **No adaptive/graduated trust posture over time.** `AuditGate`'s checks are static regardless of Sim's own accumulated track record — there's a failure-triggered *tightening* (the circuit breaker) but nothing that *loosens* any check based on a sustained good record, unlike Claude Code's measured rise in auto-approve rate over a user's first hundreds of sessions. Worth deferring deliberately for now: loosening a self-modification safety gate based on Sim's own self-reported track record is exactly the kind of change that should go through a human decision explicitly (matching this project's own established practice of taking safety-gate changes to the creator directly, e.g. this session's own scoping of the sandbox-execution check to skill subjects only), not something to build speculatively ahead of that conversation.

## If prioritizing where to spend effort next

In rough order of leverage-per-effort: **#2 (a cheap first compaction layer)** is the smallest, most mechanical addition with real near-term payoff as project children get larger. **#5 (an iterative evaluator-optimizer loop inside a single task attempt)** is a moderate change to `verify_task_completion`'s calling convention with a real chance of recovering more good-but-imperfect drafts. **#3 (a staleness/re-grounding check for project children)** matters specifically as soon as projects start genuinely spanning long real-world time, which the newly-added autonomous project-proposal path (this session's own harness work) makes more likely going forward, not less. **#1 (an explicit plan-and-narrate step for large/risky patches)** is the most valuable transparency win but also the most design work, since it has to fit alongside the existing auto-apply policy rather than contradict it.
