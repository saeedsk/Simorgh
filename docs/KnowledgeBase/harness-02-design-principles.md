# General Agent-Harness Design Principles

Source: [Building Effective Agents (Anthropic)](https://www.anthropic.com/engineering/building-effective-agents).

## Workflows vs. agents: the foundational distinction

Anthropic's framework draws one line before anything else: **workflows** are systems where the LLM and tools are orchestrated through *predefined code paths* — the sequence of steps is fixed by the harness, even if what happens inside each step is model-generated. **Agents** are systems where the LLM *dynamically directs its own process and tool usage*, retaining control over how many steps happen and in what order. Both are "agentic systems" in the broad sense; the distinction is about who — code or model — decides the control flow.

The practical guidance is blunt: **start with a workflow, and only graduate to an agent when the task genuinely can't be predicted in advance.** Workflows offer predictability and consistency for well-defined tasks. Agents earn their added cost and error-compounding risk only when the number and shape of required steps genuinely can't be known ahead of time. This is not a purity preference — it's a direct cost argument: an agent trades latency and cost for flexibility, and that trade is only worth making when flexibility is actually needed.

## Three principles that precede any specific pattern

1. **Simplicity.** The docs are explicit that effective agents are "typically just LLMs using tools based on environmental feedback in a loop" — not a complicated bespoke architecture. Complexity should be added only when a simpler version has demonstrably fallen short, and removed again the moment it stops earning its keep.
2. **Transparency.** Show the agent's planning steps explicitly, to the user and to whoever maintains the system — a black-box agent that "just does things" is much harder to debug, trust, or improve than one whose intermediate reasoning and plan are visible.
3. **Tool documentation and testing as a first-class discipline.** Anthropic's own language: invest in the "agent-computer interface" (ACI) with the same rigor normally reserved for human-computer interfaces. This was proven decisive in their own SWE-bench agent work — the tool's *description* is as much a design surface as its implementation.

## The five composable workflow patterns

These are not mutually exclusive — real systems compose them.

1. **Prompt chaining.** Decompose a task into a sequence of LLM calls where each call's output feeds the next, with optional programmatic checks between steps (a gate that validates output before it's allowed to proceed). Best when a task cleanly decomposes into fixed subtasks and trading some latency for higher accuracy is worth it. *Examples: draft marketing copy, then translate it in a second, separate call; generate a document outline, get it checked against a rubric, then write the full document from the approved outline.*
2. **Routing.** Classify the input first, then send it down a specialized path with its own tailored prompt and tools. Effective when a task has genuinely distinct categories that are better handled by different specialized processes than one generalist prompt, provided classification itself is reliable. *Examples: route customer-service queries to different specialized flows by category; route simple queries to a cheaper/faster model and complex ones to a stronger one, for cost and latency optimization.*
3. **Parallelization**, in two forms:
   - **Sectioning** — break a task into independent subtasks run in parallel, then combine results. *Examples: run content-safety screening and response-generation simultaneously rather than serially; evaluate several independent dimensions of a response (accuracy, tone, safety) as separate parallel passes.*
   - **Voting** — run the *same* task multiple times (often with some variation) and aggregate for a more confident answer. *Examples: multiple independent security-focused code reviews of the same diff, flagging anything any one pass caught; multiple independent judgments on whether content is appropriate, deciding by majority.*
4. **Orchestrator-workers.** A central LLM dynamically breaks a task into subtasks *at run time* — unlike prompt chaining, the subtasks aren't fixed in advance — delegates each to a worker LLM, and synthesizes the results. Best specifically when the required subtasks genuinely can't be predicted ahead of the actual input. *Examples: a coding task that touches an unknown-in-advance set of files, discovered only by exploring the codebase; a research task that needs to pull from a variable, input-dependent set of sources.*
5. **Evaluator-optimizer.** One LLM generates a candidate; a second, separately-prompted LLM evaluates it against explicit criteria and returns feedback; the generator revises; repeat until the evaluator is satisfied or a bound is hit. Works well specifically when there are clear evaluation criteria *and* there's demonstrated evidence that iterative feedback actually improves the output (not every task benefits from another pass). *Examples: literary translation, where nuance is genuinely hard to get right in one pass and a second "does this read naturally and preserve meaning" pass catches real misses; complex search tasks needing multiple rounds of "is this actually what was asked, or should the query be refined."*

Sim's own `verify_task_completion` (see `src/orchestrator/verification.py`) is a direct, if narrower, instance of the evaluator-optimizer pattern — a second, independently-prompted call reviewing a first call's output — without yet the "generate, get feedback, regenerate" iterative loop the full pattern describes (see file 04 and file 06).

## Tool design as agent-computer interface design

- **Give the model room to reason before committing to output.** A tool interface that forces a terse, immediately-final answer format produces worse results than one that lets the model reason first, because reasoning tokens spent before the answer measurably improve the answer.
- **Prefer formats the model has seen a lot of.** Markdown, or a shape close to natural code, beats a bespoke DSL the model has to learn from the prompt alone — this is precisely why Sim's own SEARCH/REPLACE edit-block format (this session's own milestone 90) deliberately copied the exact conflict-marker shape from real merge conflicts and tools like Aider, rather than inventing a new one: the model has already seen that shape thousands of times in training.
- **Eliminate pure formatting overhead** — anything that requires the model to do bookkeeping unrelated to the actual task (counting exact line numbers, computing diff-chunk headers by hand, precise character-escaping) is a place errors concentrate for no real benefit; either the harness should compute that bookkeeping itself, or the format should avoid needing it.
- **Write tool documentation like you're documenting for a junior developer who's never seen the codebase.** Explicit example usage, explicit edge cases, explicit boundaries of what the tool will and won't do — the same rigor as writing a good docstring for a human teammate, not a terse one-liner.
- **Apply poka-yoke (mistake-proofing) to the tool's own argument shape.** If a class of mistake is common, redesign the interface so that mistake becomes structurally impossible rather than just discouraged in the description — e.g. requiring absolute file paths specifically because relative paths cause directory-context confusion in practice, not in theory.
- **Test tools empirically, not just by inspection.** Run many varied real inputs through the tool, watch where the model actually goes wrong, and iterate the interface based on those observed failures — the same "live-caught, then fixed" discipline this project's own `docs/EVOLUTION.md` log already practices throughout.

## When (not) to reach for a framework

The guidance here is pointed: many of the patterns above work in "a few lines of code" using a raw model API directly. Frameworks (the docs name Claude Agent SDK, AWS Strands, Rivet, Vellum as examples) can reduce boilerplate for standard patterns, but they also add a layer of abstraction that can obscure exactly what prompts and responses are actually happening underneath — and *incorrect assumptions about what a framework is doing under the hood is a genuine, repeated source of production bugs*. The recommendation: understand the underlying API-level mechanics regardless of whether a framework sits on top, and reach for a framework only once a hand-rolled version has proven the pattern is worth the added structure.
