# Driving to Real Completion: Verification and Avoiding Stalls

Sources: [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works) (verify-results phase, checkpoints), [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) (evaluator-optimizer), [LLM Agent Evaluation Metrics in 2026](https://www.confident-ai.com/blog/llm-agent-evaluation-complete-guide), [Auto-Eval Judge: Towards a General Agentic Framework for Task Completion Evaluation](https://arxiv.org/pdf/2508.05508), [Plan Verification for LLM-Based Embodied Task Completion Agents](https://arxiv.org/pdf/2509.02761).

## "It ran" is not "it's done"

The most common failure mode in agentic systems without a real verification layer is conflating *the action executed without error* with *the goal was actually achieved*. A patch that applies cleanly, a script that exits 0, a file that got written — none of these are evidence the underlying intent was satisfied. The evaluation literature is explicit about this: task completion is fundamentally "a semantic judgment over the whole run" — it needs the overall input and the final output together, not just a per-step success signal, because a run can succeed at every individual step and still miss the actual point.

This distinction maps directly onto the difference between Sim's own `AuditGate`/isolated-test-suite (does this change do anything *dangerous*, and does it break anything *already covered by a test*) and `verify_task_completion` (does this change actually address what the task was *for*) — two genuinely different questions, and a harness needs both, because passing one says nothing about the other. A mechanically clean change that misses the point should never count as done just because nothing broke.

## Verification as a separate, independently-prompted pass

The evaluator-optimizer pattern (file 02) is the general shape; the concrete implementation detail worth calling out is that the *evaluator* should be a genuinely separate prompt/call from the one that produced the work — not the same context continuing to grade its own output. A model reviewing its own immediately-prior output in the same context tends to rationalize what it just did rather than genuinely re-examine it; a fresh, separately-framed call ("here is a task and a claimed result — does this actually address it, yes or no, and why") is meaningfully more likely to catch a real miss. This is exactly why Sim's `verify_task_completion` is architected as its own function taking `(task, result)` and making its own independent `cognition.complete()` call, rather than being folded into the same drafting call that produced the result.

## Checklist-based verification beats a single holistic judgment

Rather than asking an evaluator one large "is this good?" question, the more reliable pattern generates a small set of concrete, binary (yes/no) checklist questions specific to the task first, then evaluates each one independently: did it address requirement A? Requirement B? Did it avoid doing X, which was explicitly out of scope? A single holistic judgment is prone to a strong-sounding result overriding a real but easy-to-miss gap; a checklist forces each requirement to be checked on its own terms. The evaluation literature also recommends a genuine third category beyond yes/no where appropriate — "insufficient evidence" or "needs review" — rather than forcing a binary call when the evaluator genuinely can't tell; a forced binary on insufficient evidence just adds confident-sounding noise.

## Evaluate the trajectory, not only the final artifact

Beyond "is the final output right," a thorough evaluation also looks at *how* the result was reached: was tool choice sensible, were there redundant or wasted steps, did the agent recover reasonably from an error along the way, or did it flail? A result can be correct by accident after a chain of bad decisions that happened to still land somewhere useful — that's a different, weaker signal than a result reached by a clean, well-justified path, and a harness that only ever checks the final artifact never learns the difference. This matters specifically for a system meant to *improve itself* (as Sim's own reflection/self-critique work this session is starting to do): a trajectory-blind evaluator can't tell "worked, and worked well" apart from "worked, but got lucky," and only the former is a pattern worth reinforcing.

## Non-answers must never be silently graded as failures

A concrete, live-caught failure mode (this session's own milestone 92): an evaluator asked to answer strictly "YES or NO first" can instead narrate ("I'll check the file...") without ever actually answering, and a parser that only accepts a strict first-word match will silently read that non-answer as a rejection — wrongly blocking work that was never actually reviewed at all. The general principle: a verification layer must distinguish *"I reviewed this and it's wrong"* from *"the reviewer didn't produce a clear verdict"* — the second case should defer to whatever mechanical checks already passed (or, absent those, to a human), never collapse into "reject." Treating silence as failure is a systematic bias against process — a class of error, not a one-off bug — because any transient reviewer confusion becomes a false rejection instead of a shrug.

## What "done" should actually mean for a multi-step project

For a single task, done means: the action was taken, it passed whatever mechanical gates apply, and an independent check confirms it addresses the original ask. For a *project* (file 03), done needs one more property: **every child step reached a real terminal state, and the terminal states collectively satisfy the goal** — not just "no child is still pending." A project where every child eventually finished but several failed outright is not "done" in any meaningful sense, even though nothing is technically still in progress; a rollup that only checks "nothing pending" rather than "everything succeeded" will happily report a half-broken project as complete. Sim's own `project_status()` (`src/orchestrator/projects.py`) already gets this right structurally — it returns `DONE` only when every child is `DONE`, and a separate `FAILED` state when every child is terminal but at least one failed — precisely so a stalled-but-technically-finished project can't be mistaken for a successful one.

## Avoiding silent stalls

A multi-step effort can fail to reach either DONE or a clean FAILED state and instead just... stop being worked on, with nothing forcing anyone to notice. The concrete mechanisms that prevent this:

- **A bounded retry count with an explicit terminal give-up state.** A step that keeps failing shouldn't retry forever (wasting resources) or silently vanish from the backlog after one failure (losing the work entirely) — it should retry up to a stated bound, then transition to an explicit "gave up after N attempts" terminal state that's visible in whatever surfaces the backlog. Sim's `MAX_BLOCKED_RETRY_ATTEMPTS`/`_reconsider_blocked_tasks` is exactly this pattern.
- **Rollback/recovery when a multi-step effort fails partway.** If steps 1–3 of a 5-step project succeeded and step 4 fails unrecoverably, the harness needs an explicit policy: does the project stay at "3/5 done, permanently blocked on step 4," accepting the partial state, or does something roll steps 1–3 back too? Both are legitimate answers depending on the domain, but *not deciding* — leaving a half-applied, half-abandoned project with no stated status — is the actual failure mode to avoid. Claude Code's own answer for a batch of related changes that fails its own final check is to revert the whole batch as new commits (never rewriting history) rather than leave a partially-applied, ambiguous state; Sim's own `evolve`/`propose_patch_batch` pipeline already does the equivalent (`revert_commits_since`, a multi-commit range revert on a failed post-batch self-check).
- **Make "stalled" itself a detectable, queryable state**, not something only discoverable by an operator happening to notice nothing has moved in a while. A project sitting at "in progress" with its current child blocked and no further retries scheduled is functionally stalled — a harness's own status surface (a `tasks` command, a dashboard, a digest) should be able to say so plainly, rather than reporting "in progress" indefinitely with no distinction from genuinely active work.
